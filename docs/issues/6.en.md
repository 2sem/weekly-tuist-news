# Weekly Tuist News #6

> Note: this is a draft. Translated from the approved Korean draft. Not yet published to Medium.

---

This issue covers two CLI releases, 4.213.0 and 4.214.0. There were a lot of fixes, but what regular users will probably feel most are the cache reliability fixes and the CI-side improvements. There is also a new, safer way to install the CLI.

**1. CLI 4.213.0 (10/21): module cache uploads and generation reliability**

- Large module cache blobs are now split into chunks and spliced together on upload.
- Module cache entries that the remote evicted during a cache warm are now uploaded again.
- Fixed xcproj target identifiers changing on every generation, so the identifiers now stay the same between runs.
- Local packages can now override registry packages that live under a different directory name.
- Redundant static product checks are now skipped when only one target links the product, which cuts unnecessary checks.
- Invalid values for options are now rejected when the option is set through an environment variable.

Also in this release: Git history collection on CI (including TeamCity) and improvements to coverage uploads.

Source: [4.213.0 release notes](https://github.com/tuist/tuist/releases/tag/4.213.0)

**2. CLI 4.214.0 (10/26): many cache fixes, per-target Build For settings in schemes**

This is the biggest release of the issue, and it is mostly fixes.

- Manifest caches are now reused across fresh checkouts.
- The compilation cache is now restored even after the local cache has been wiped several times.
- The workspace path that Xcode uses when locating DerivedData under `/private` is now what gets hashed.
- Project prefix mapping is now left off when `enableCaching` is on.
- Schemes can now take per-target Build For settings.
- Fixed `--json` output and errors being silently dropped.
- Previews gained tracks and release notes.

On coverage, a way to choose the coverage variant of the binary cache through the `coverage` generation option in `Tuist.swift` and the `TUIST_COVERAGE_ENABLED` environment variable has landed. However, according to the code it only works when the `COVERAGE` client feature flag is on (early access), so this issue does not cover how to use it.

Source: [4.214.0 release notes](https://github.com/tuist/tuist/releases/tag/4.214.0)

**3. Install signed CLI releases and verify them with mise**

Every new CLI release (backports included) now ships a `packslip.sigstore.json` on its GitHub release. mise uses this manifest to confirm the identity of the release workflow, and checks that the downloaded archive matches the signed digest before installing. It works out of the box with mise 2026.9.2 or newer, with no separate CLI or setting.

```bash
mise use packslip:github.com/tuist/tuist@latest
```

`mise use tuist` currently uses the Aqua backend, so it does not switch to Packslip automatically; to get verification you need the `packslip:` identifier. Existing installation methods keep working, and releases published before this are not retroactively signed.

Source: [changelog 2026.10.17](https://tuist.dev/changelog/2026.10.17-signed-cli-releases)

**Tuist Talk: shouldn't the module cache miss when the Xcode version changes?**

In the public Tuist Slack, a user running Xcode 27.0 and 27.1 side by side asked about module cache binaries built with one Xcode being used as-is with the other, which caused problems. The answer from the Tuist team was that this had already been fixed, and that the CLI version in use might simply not include the fix. The fix is [PR #13666](https://github.com/tuist/tuist/pull/13666), which includes the Xcode build information in the cache key, and they suggested either upgrading to the latest version or using the backport in 4.207.1.

The cause was that Xcode releases shipping the same compiler produced the same hash even when their SDK builds differed. The fix is in 4.211.0, and after upgrading, existing cache entries miss once (because the hash gains one more input).

If you mix Xcode betas or minor updates, checking your CLI version first is worth it. Source: [Slack thread](https://tuist-community.slack.com/archives/C018QG7U7SN/p1792586534629089)

I ran the command from item 3 myself. Pinning the version to 4.214.0 failed to install, while `@latest` worked (the version it installed was 4.214.1). The output when pinned looked like this.


```
✗ installed 0 tools · 1 failed in 815ms
mise ERROR Failed to install packslip:github.com/tuist/tuist@4.214.0: github.com/tuist/tuist has no release 4.214.0 carrying packslip.sigstore.json; mise installs from a packslip and does not guess at release assets
```

Checking on GitHub, the 4.214.0 release does carry `packslip.sigstore.json`, so I don't know the cause yet. If you want to pin a version, I'd suggest trying it with this in mind.
